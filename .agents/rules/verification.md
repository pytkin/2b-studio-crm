# Локальный маршрут проверок

## Текущий этап

Приложение проверяется командой `rtk proxy pnpm verify`. Для изменений базы
и сквозного поведения дополнительно пройдите проверки с настоящим Supabase
по [командам проекта](../../README.md#команды). Один исполнитель управляет
общей тестовой БД. `rtk proxy ./bin/project verify` также проверяет Kit и
документацию. Фактические результаты ведёт [матрица](../../docs/acceptance-plan.md).

## TDD для кодовых задач

Для нового или изменённого поведения React, адаптера, SQL/RLS/RPC, миграции
или исполняемой команды проходи цикл **RED → GREEN → REFACTOR** для одного
наблюдаемого эффекта за раз. Для дефекта первый тест воспроизводит дефект.

1. **RED, до реализации:** из карточки задачи возьми роль, исходное состояние,
   действие и ожидаемый результат. Напиши исполняемый тест на границе владельца,
   запусти и убедись, что он упал именно из-за отсутствующего/неверного поведения.
   Для запретов проверь также разрешённый контроль: отказ всем пользователям
   не доказывает правильность политики. Неисправный runner, Docker, авторизация
   фикстуры или сеть не засчитываются. Подготовку тестового окружения можно
   сделать первой. Если тест неожиданно зелёный, проверь, что он различает
   требуемое и ошибочное поведение; не придумывай RED и не пиши лишний код.
2. **GREEN:** внеси минимальное изменение у владельца и повтори тот же тест
   без ослабления утверждений. Для записи в БД проверяй также сохранённое
   состояние и отсутствие побочных изменений при отказе.
3. **REFACTOR:** упрости код при необходимости, повтори этот тест и относящиеся
   регрессионные проверки. При чистом рефакторинге сначала зафиксируй текущее
   поведение проходящим тестом; искусственный RED не нужен.

В конце соответствующей карточки [плана](../../docs/implementation-plan.md)
добавь фактическую запись: `тест/граница | команда | RED: наблюдавшееся
расхождение | GREEN: результат повторного запуска | REFACTOR: изменения
или «не требовался», итог проверок`. Отдельные Git-коммиты не требуются.
До запуска текст «первый RED» в плане — проект теста, а не свидетельство.
Документирование, установка зависимостей, ручная приёмка и выкладка имеют
свои проверки результата. Если в такой задаче возникает исполняемая логика,
примени к ней этот цикл до написания кода.

## При реализации приложения

- Начинать с изменённой границы и [матрицы приёмки](../../docs/acceptance-plan.md).
  Не превращать будущие команды в успешные заглушки или декларацию покрытия.
- Frontend: Vitest + React Testing Library; MSW только для поведения интерфейса
  на границе API. Мок не подтверждает RLS или атомарность базы.
- База: pgTAP против мигрированной локальной БД; REST/RPC-проверки через
  пользовательские сессии Supabase SDK. Привилегированный клиент может готовить
  изолированные фикстуры, но не выполнять защищаемое действие вместо пользователя.
- Браузер: Playwright для входа, маршрутов, роли и полного цикла задачи.
  Desktop 1440×900 и mobile 360×800; клавиатура, ошибки и фокус по сценарию.
- Для auth, RLS, RPC и истории получать независимый read-only взгляд; итоговая
  приёмка также независимая. После обычного изменения достаточно self-review
  и соразмерных проверок, если выявленный риск не требует большего.
- При изменении допуска ключа или HTTP-проверки защиты чтения дополнительно
  запускай `rtk proxy pnpm test:mutation`. Для остальных запретов выбирай
  конкретную ошибку (например, снятие проверки владельца): разрешённый контроль
  должен остаться зелёным, а тест запрета — упасть по ожидаемой причине. Примеры
  и границы этой проверки — в [отчёте](../../docs/evidence/negative-mutation.md).
- Рецензент получает цель, конечные артефакты и первичные требования в чистом
  контексте. Подтверждённые P0–P2 исправляются до передачи результата.
- Результаты записывать в план разработки: требование, реализация, команда,
  наблюдаемый результат и предел свидетельства. Не объявлять облачное или
  пользовательское поведение проверенным по локальной сборке.

Используются подходы Seller Platform по разделению уровней доказательств и
проверкам реальной persistence-границы. Его Advisor, coverage-пилоты, backend
тесты и команды не переносятся.
