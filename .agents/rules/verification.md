# Локальный маршрут проверок

## Текущий этап

Команда текущего handoff — `rtk proxy ./bin/project verify`. Её границы и
реальные результаты ведёт [таблица подключения](../../docs/agent-platform-onboarding.md).
Поведенческие тесты CRM, сборка и браузерная приёмка ещё не существуют.

## При реализации приложения

- Начинать с изменённой границы и [матрицы приёмки](../../docs/acceptance-plan.md).
  Не превращать будущие команды в успешные заглушки или декларацию покрытия.
- Frontend: Vitest + React Testing Library; MSW только для поведения интерфейса
  на границе API. Мок не подтверждает RLS или атомарность базы.
- База: pgTAP против мигрированной локальной БД; REST/RPC-проверки через
  пользовательские сессии Supabase SDK. Привилегированный клиент может готовить
  изолированные фикстуры, но не выполнять защищаемое действие вместо пользователя.
- Браузер: Playwright для входа, маршрутов, роли и полного цикла задачи.
  Desktop 1440×900 и mobile 360×800; клавиатура, ошибки и фокус по сценарию.
- Для auth, RLS, RPC и истории получать независимый read-only взгляд; итоговая
  приёмка также независимая. После обычного изменения достаточно self-review
  и соразмерных проверок, если выявленный риск не требует большего.
- Рецензент получает цель, конечные артефакты и первичные требования в чистом
  контексте. Подтверждённые P0–P2 исправляются до передачи результата.
- Результаты записывать в план разработки: требование, реализация, команда,
  наблюдаемый результат и предел свидетельства. Не объявлять облачное или
  пользовательское поведение проверенным по локальной сборке.

Используются подходы Seller Platform по разделению уровней доказательств и
проверкам реальной persistence-границы. Его Advisor, coverage-пилоты, backend
тесты и команды не переносятся.
