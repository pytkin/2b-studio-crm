# Техническая спецификация мини CRM

Статус: целевая архитектура принята к реализации, 2026-11-04.
Контракты реализации проверяются по [плану приёмки](acceptance-plan.md). Продуктовый объём задают
[требования](business-requirements.md), а происхождение решений —
[журнал](decisions.md).

## Архитектура

Браузерная SPA обращается к Supabase Auth и Data API через официальный
Supabase SDK. PostgreSQL владеет данными, полномочиями, переходами и историей.
Отдельного backend-сервиса, workers или AI-функций для v1 не требуется.

Чтение бизнес-таблиц ограничивает RLS. Изменяющий API — семь узких database RPC;
прямые INSERT, UPDATE и DELETE для клиентских ролей отозваны. Клиент показывает
доступные действия, но окончательное решение всегда принимает база.

## Frontend

Один пакет с `src/app` для маршрутов и провайдеров, `src/modules/auth`,
`src/modules/objects`, `src/modules/tasks` для сценариев и `src/shared` для
реально повторяемых UI-примитивов и интеграционной инфраструктуры.
Модули публикуют явные точки входа; доменная логика не уходит в общий каталог.

| Область | Решение |
|---|---|
| Сборка и язык | Vite, React, TypeScript strict |
| Маршруты | TanStack Router |
| Серверное состояние | TanStack Query |
| Формы и ввод | React Hook Form, Zod |
| Интерфейс | Tailwind, app-local компоненты shadcn/Radix |
| Данные | Supabase SDK, типы из мигрированной схемы |
| Тесты | Vitest, React Testing Library, MSW, Playwright |

Совместимые версии закреплены в [manifest](../package.json) и [lockfile](../pnpm-lock.yaml). XState, React Compiler pilot,
монорепозиторий, NestJS и Go в согласованный стек не входят.

### Маршруты и состояние

| URL | Доступ и содержание |
|---|---|
| `/login` | Вход; активная сессия переводит на разрешённый экран |
| `/objects` | Список доступных объектов |
| `/objects/$objectId` | Объект и доступные задачи; действия постановщика |
| `/tasks/$taskId` | Данные, действия по роли и статусу, история |
| `/my-tasks` | Задачи текущего исполнителя |
| `/` | Постановщик → объекты; исполнитель → мои задачи; гость → вход |

Формы создания и редактирования размещаются в контексте списка или карточки;
отдельные публичные URL для них не обязательны. Меню и маршруты не открывают
управление аккаунтами. Переход по прямой ссылке проходит ту же авторизацию.

Сервер проверяет права при каждом новом запросе. На клиенте повторное чтение
доступа обязательно при входе на маршрут, возвращении фокуса во вкладку,
восстановлении сети и действии из открытой карточки. Перед изменением
проверяются доступ и версия, с которой пользователь начал редактирование. Новую версию
нельзя молча подставлять в отправляемую правку; гонку между чтением и записью закрывает
сам RPC. Чужой сессии не обещается мгновенная доставка события. При подтверждённой
недоступности убрать карточку, историю, черновик и устаревшие списки; поздний
ответ прежнего запроса не может вернуть их на экран. Сетевой отказ сам по себе
не означает отзыв прав. До разрешения неопределённости запись не отправлять.

Сессию предоставляет SDK, активную роль — защищённый профиль БД. До определения
сессии и профиля защищённые данные не отображаются. Query keys включают ID
текущего пользователя; при выходе, смене пользователя или потере доступа
связанные запросы отменяются и кеш очищается. Данные кеша не являются
доказательством сохранённого доступа на сервере.

UI-состояние форм локально. Статус задачи не меняется оптимистически:
отображается подтверждённый ответ БД, затем инвалидируются карточка,
история и затронутые списки. Изменяющие запросы не имеют автоматических retry.

## Данные и API

Схема создаётся [миграциями PostgreSQL](../supabase/migrations).
UUID используются для бизнес-записей и профилей, время хранится как
`timestamptz`, формируется БД и отображается в часовом поясе браузера с русской
локалью. Внешние пробелы обязательного ввода удаляются; пустое название,
адрес или обязательный комментарий не принимаются. Описание необязательно.
Пользовательский текст отображается как текст, без исполнения HTML.

### Сущности

| Сущность | Основные поля и ограничения |
|---|---|
| `profiles` | `id` → Auth user, `display_name`, `role` (`manager` или `executor`), `active`; клиент не создаёт и не меняет профиль, роль или активность |
| `objects` | `id`, `name`, `address`, `version`, `deleted_at`; обязательные имя и адрес |
| `tasks` | `id`, `title`, `description`, `object_id`, `assignee_id`, `status`, `author_id`, `created_at`, `version`, `deleted_at`; объект и назначенный активный исполнитель обязательны |
| `task_status_history` | Серверный последовательный `id`, `task_id`, `actor_id`, `occurred_at`, `from_status`, `to_status`, `comment`; клиент не задаёт поля события |

`version` начинает с 1; успешная операция изменения или мягкого удаления
увеличивает её на 1 у каждой затронутой активной записи. Автор и дата создания задачи неизменяемы.
Для отображения имени автора
в задаче и имени участника в истории БД сохраняет их текстовые снимки при
создании записи; клиент не может подставить эти значения. Это позволяет читать
историю без открытия исполнителю чужих профилей или каталога аккаунтов.
Изменение имени аккаунта не переписывает исторические снимки.

Профили сохраняются при деактивации аккаунта; через приложение аккаунты не
удаляются. Внешние ключи истории не используют каскадное физическое удаление.
Индексы нужны по связям задачи с объектом и исполнителем, по истории задачи
и по условиям RLS; конкретный набор проверяется запросами реализации.

### Статусы

| Значение БД | Отображение |
|---|---|
| `new` | Новая |
| `in_progress` | В работе |
| `in_review` | На проверке |
| `accepted` | Принята |
| `rework` | На доработке |

Граф и роли переходов канонически заданы в
[требованиях](business-requirements.md#жизненный-цикл-задачи).
Создание задачи включает начальное событие `NULL → new` в той же транзакции.
Редактирование, перенос, переназначение и мягкое удаление не создают фиктивных
переходов. Отдельный аудит редактирования полей в объём v1 не входит.

### Чтение

SDK читает `objects`, `tasks`, `task_status_history` с RLS. История сортируется
по серверному последовательному ID от старых событий к новым. Профиль доступен
самому пользователю; постановщик также читает минимальный справочник профилей
для назначения активных исполнителей. Auth emails и административные поля
не включаются в публичный справочник. Исполнитель не получает чужие профили;
необходимые имена входят в снимки доступной ему задачи и её истории.

Списки, вложенные ответы и счётчики считают только видимые записи.
Точный счётчик с фильтром запрашивается через `select=count` без заголовка `Prefer`;
вложенный `tasks(count)` остаётся доступен. Для клиентского GET/HEAD к CRM с
`Prefer`, включая SDK-опцию `{ count: 'exact', head: true }`, сервер отказывает.
PostgREST использует [статистику планировщика для planned/estimated](https://docs.postgrest.org/en/stable/references/api/pagination_count.html#planned-count).
При повторяющемся заголовке значение, видимое в SQL, может отличаться от
выбранного API. Поэтому проверка заголовка по одному только его значению небезопасна. Нельзя
возвращать исполнителю общий счётчик задач объекта или чужую историю через
вспомогательный запрос, view или RPC. Отдельный поиск чужих задач по ID
не создаётся.

### Изменяющие RPC

Имена аргументов ниже используются в вызове SDK. `p_id` и ссылки на записи —
UUID; `p_expected_version` — положительное целое из прочитанной версии.
Версия и все поля снимка ответа — значения после успешной записи. Ответ —
один объект; ключи `object`, `task` и `event` содержат соответствующие записи
из [модели данных](#сущности).

| Операция | Аргументы запроса | Ответ при успехе |
|---|---|---|
| `create_object` | `p_id, p_name, p_address` | `{object}` |
| `update_object` | `p_id, p_expected_version, p_name, p_address` | `{object}` |
| `delete_object` | `p_id, p_expected_version` | `{id, version}` удалённого объекта |
| `create_task` | `p_id, p_title, p_object_id, p_assignee_id, p_description, p_comment` | `{task, event}` с начальным событием |
| `update_task` | `p_id, p_expected_version, p_title, p_object_id, p_assignee_id, p_description` | `{task}` |
| `delete_task` | `p_id, p_expected_version` | `{id, version}` удалённой задачи |
| `transition_task` | `p_id, p_expected_version, p_to_status, p_comment` | `{task, event}` с событием перехода |

Названия, адрес, описание и комментарий — текст, целевой статус — одно из
значений БД. Все перечисленные аргументы обязательны, кроме `p_comment`.
Поля редактирования передаются целиком; для отсутствующего описания передать
пустую строку. При создании задачи `p_comment` относится к начальному событию, не к описанию задачи.
Комментарий можно не передавать или передать `null`, кроме
возврата на доработку: там нужна непустая после удаления внешних пробелов причина.

Первые шесть операций разрешены только постановщику. В `transition_task`
роль, текущее назначение и переход проверяются по графу. Идентификатор
действующего пользователя всегда берётся из Auth, а не аргумента RPC.
Клиент не передаёт автора, дату, from-status, произвольный role или событие
истории. Поля каждого RPC явно перечислены; массового обновления произвольным
JSON-объектом нет. БД валидирует обязательный ввод независимо от Zod.

Перед первым запросом создания клиент генерирует UUID объекта или задачи и
сохраняет его в текущем черновике вместе с отправляемыми полями. Повтор того же
намерения использует тот же ID. Create выполняет только вставку: существующий
ID даёт отказ без перезаписи, повторного события истории или выдачи недоступной
записи; `upsert` для этого пути не используется. Одинаковые названия и поля
у разных записей допустимы и не служат способом корреляции.

### Что проверять для каждого RPC

Назначение — только
на действующего исполнителя. UUID новой записи генерирует клиент. БД назначает
версии и время мягкого удаления. Для задачи БД задаёт автора, время создания
и начальный статус; для события — ID, автора, время и снимок имени. При
переходе предыдущее состояние берётся из заблокированной строки. Ни один отказ RPC не меняет бизнес-записи или историю.
Следующие случаи проверяются под реальными правами; до/после сверять и число строк.

| RPC | Разрешённый результат | Контрольный отказ и состояние после него |
|---|---|---|
| `create_object` | Постановщик получает активный объект с переданным ID и v1; создана ровно одна строка объекта | Пустой адрес → INVALID_INPUT; повтор занятого UUID → ID_UNAVAILABLE независимо от доступности прежней строки. Ни вставки, ни перезаписи |
| `update_object` | На активном объекте v меняются только рабочие поля и версия до v+1; задачи неизменны | Видимый объект и старая версия → CONFLICT; не менять имя, адрес или версию |
| `delete_object` | ID и v+1; все активные дочерние задачи помечены удалёнными и получают +1; ранее удалённые и события не изменены | Уже удалённый объект → UNAVAILABLE; неверная версия видимого → CONFLICT, все дочерние строки неизменны |
| `create_task` | Инициатор-постановщик — автор; активная задача v1, статус new, ровно одно событие NULL → new с тем же актором и переданным комментарием (либо `null`) | Недоступный объект → UNAVAILABLE; недействительный исполнитель → INVALID_INPUT; занятый UUID → ID_UNAVAILABLE. Нет второй записи или события |
| `update_task` | Постановщик переносит/переназначает доступную задачу в любом статусе; v+1, статус, автор, дата создания и события прежние | Устаревшая версия видимой задачи → CONFLICT; удалённый целевой объект → UNAVAILABLE. Исходная принадлежность и версия сохранены |
| `delete_task` | ID и v+1; удаляется из рабочих списков только эта задача. История сохраняется, права на объект пересчитываются | Старая версия видимой задачи → CONFLICT; уже удалённая → UNAVAILABLE. Нет нового события или повторного увеличения версии |
| `transition_task` | Разрешённое ребро графа, правильная роль и версия: v+1 и ровно одно событие с актором, временем, обоими статусами и комментарием | Чужая задача даже со старой версией → UNAVAILABLE; недопустимое ребро → INVALID_TRANSITION; возврат с пробелами → INVALID_INPUT. Статус, версия и история неизменны |

Начальный комментарий задачи, комментарий к переходу и причина возврата принимают
до 4 000 кодовых точек Unicode включительно. Форма проверяет введённый текст,
а RPC проверяет переданное значение до сохранения события. Превышение даёт
`INVALID_INPUT`. Транзакция целиком откатывается, существующая история остаётся читаемой.

### Атомарность и конкуренция

RPC блокирует затронутые строки, проверяет доступность и ожидаемую версию
после блокировки, затем выполняет весь эффект в одной транзакции. Несовпадение
версии даёт конфликт без частичного изменения. Конкурентные status-запросы
с одной версией дают один переход и одно событие.

Изменения задач согласуются с удалением родительского объекта. Порядок
блокировок: затронутые объекты в порядке ID, затем задачи в порядке ID;
доступность объекта проверяется под блокировкой. При переносе блокируются
исходный и целевой объекты. Поэтому создание или изменение задачи не может
зафиксироваться под уже удалённым объектом. Профиль назначения проверяется
как действующий исполнитель в этой же операции.

Удаление объекта помечает его и все ещё неудалённые задачи одной транзакцией,
увеличивая их версии. История остаётся неизменной. Удалённые записи исключаются
из RLS-чтения обеих бизнес-ролей; административный доступ вне API CRM
сохраняется для обслуживания. Клиент не получает RPC восстановления.

Проверка конкуренции использует независимые соединения и управляемый
порядок транзакций, а не задержки по таймеру. Сверять результат каждого
запроса и конечные строки после завершения обеих операций:

- Два разрешённых перехода из одной версии: один успех, один конфликт,
  версия +1, одно новое событие. Две правки одной версии: сохраняются поля
  победителя, версия +1, событий нет. Для правки и перехода: событие есть
  ровно тогда, когда победил переход (проигравший может потерять и доступ).
- Переназначение против действия прежнего исполнителя: если переназначение
  первым зафиксировано, действие видит UNAVAILABLE, не версию; если первым
  прошёл переход, переназначение со старой версией даёт CONFLICT.
- Удаление объекта против создания задачи: создание первым → задача и её
  начальное событие сохранены, затем задача скрыта каскадом; удаление первым →
  создание отклонено, ни задачи, ни начального события.
- При переносе из объекта до его удаления перенесённая задача остаётся доступна
  в новом объекте; при переносе в объект до его удаления она скрыта каскадом.
  Если удаление первым скрыло задачу либо целевой объект, перенос отклоняется.
  Для перехода до каскада сохраняется одно событие; после каскада переход
  отклонён без события. Активных задач у удалённого родителя не остаётся.

## Безопасность

### Источник полномочий

Авторизация использует активный профиль БД, привязанный к `auth.uid()`.
Пользовательские `user_metadata` и аргументы запроса не задают роль.
Профиль без роли, отсутствующий или неактивный профиль не получает бизнес-доступ.
Администратор может независимо от приложения запретить новые операции,
деактивировав профиль и заблокировав аккаунт в Supabase Auth; старый JWT не
восстанавливает бизнес-доступ. Смена роли не входит в клиентский API.

### Матрица чтения

| Данные | Постановщик | Исполнитель | Гость или неактивный профиль |
|---|---|---|---|
| Неудалённые объекты | Все | Только с текущими своими неудалёнными задачами | Нет |
| Неудалённые задачи | Все | Только с текущим `assignee_id = auth.uid()` и неудалённым объектом | Нет |
| История | Для доступной задачи | Для доступной собственной задачи | Нет |
| Профили | Свой и минимальный справочник | Только свой | Нет бизнес-доступа |
| Мягко удалённые записи | Нет через API CRM | Нет | Нет |

Политики задач и объектов не должны рекурсивно вызывать друг друга.
Если для роли или проверки видимости нужна вспомогательная функция,
она размещается в неэкспонируемой схеме `private`, проверяет текущий Auth ID
и не предоставляет произвольный обход RLS. Такие функции отдельно тестируются.

### Grants и функции

RLS включается на всех четырёх таблицах. У `anon` отзываются бизнес-права;
у `authenticated` остаётся только допустимое чтение. Прямые клиентские
INSERT, UPDATE и DELETE бизнес-таблиц и истории отзываются, включая возможность
изменить `role`, `deleted_at`, `version` или системные поля. Только служебные
пути создания пользователей и миграций используют привилегированную среду.

Изменяющие RPC используют `SECURITY DEFINER`, пустой `search_path` и полностью
квалифицированные имена. Они явно проверяют Auth, активный профиль, роль,
видимость ресурса, версию, ввод и переход; definer сам по себе не сохраняет
защиту RLS. `EXECUTE` отзывается у `PUBLIC` и `anon`; нужные функции выдаются
только `authenticated`. Права по умолчанию также закрываются для новых функций.
Вспомогательные функции не превращаются в доступный извне универсальный SQL API.

Историю вставляет только доверенный путь создания задачи или status-RPC.
Ни одна бизнес-роль не может создать произвольное событие, обновить или удалить
старое через прямой API или другой RPC. Ошибка вставки истории откатывает статус.

### Ключи и сессия

В браузере допустимы только публичный URL Supabase и publishable key
(либо эквивалентный публичный local anon key). `service_role`, secret key,
пароль БД и административные токены не входят в bundle, tracked-файлы,
логи или отчёты. Локальные env-файлы игнорируются, в примерах — только имена
переменных. При работе с session cache учитываются смена аккаунта и поздние
ответы отменённых запросов. Пользовательский текст отображается без HTML.

## Ошибки и согласованность

Доменный отказ — ошибка RPC с безопасным машинным идентификатором
(`message` из фиксированного перечня ниже); UI переводит его в русский текст.
Прямой запрет grants, отказ Auth и пустой результат SELECT под RLS имеют
собственный транспортный результат: адаптер не требует от них ошибки
из тела RPC. Чтение чужой и отсутствующей записи даёт одинаковое представление
«Запись недоступна», без ID владельца, версии или прежнего содержимого.

Порядок для запроса с корректной формой аргументов:

1. Нет сессии — требуется вход; отсутствие активного профиля или права на саму
   операцию (например, исполнитель вызывает CRUD постановщика) — FORBIDDEN
   независимо от переданного ID. Гость также может быть остановлен до RPC.
2. Нет текущего доступа к запрошенному ресурсу, в том числе после удаления
   или переназначения, — UNAVAILABLE. Для изменения задачи нельзя раскрывать
   её версию, допустимые переходы или содержимое до этой проверки.
3. Для существующей видимой записи несовпадение ожидаемой версии — CONFLICT.
   Для актуальной версии отсутствующее в графе ребро — INVALID_TRANSITION,
   правильное ребро для другой роли — FORBIDDEN, невалидные поля или пустая
   причина возврата — INVALID_INPUT. На create занятый UUID не возвращает
   существующую запись (ID_UNAVAILABLE). Технические ошибки не раскрываются
   как текст SQL; реализация S2 проверяет эти категории через реальный SDK.

### Если ответ не дошёл

Автоповтор записи выключен. После восстановления связи сначала читаются
доступные пользователю данные. Совпадение состояния не всегда доказывает,
какой именно запрос его создал. У пользователя остаётся следующий выбор:

| Действие | Что проверяем | Что показываем и можно ли повторить |
|---|---|---|
| Создание | Прочитать по UUID текущего черновика; у задачи — также начальное событие | Доступная запись открывается как сохранённая. При отсутствии видимой строки результат неизвестен; для того же намерения допустим явный повтор с тем же UUID и исходными полями. Не делать upsert, не выделять новый ID автоматически |
| Редактирование или переназначение | Сверить доступ, версию и фактические рабочие поля | Совпадение подтверждает текущие значения, но не авторство конкретной попытки. При расхождении сохранить черновик только у того же пользователя с подтверждённым доступом; показать отличия, дать заново подтвердить актуальную правку с новой версией |
| Переход статуса | Перечитать версию, текущий статус и видимую историю, включая актора и причину возврата | Показать фактические события. Не приписывать совпадающий переход конкретной попытке без доказательства. Повтор — только явный и только если действие по-прежнему разрешено из актуального состояния |
| Удаление | Перечитать карточку и разрешённый список | Исчезновение строки подтверждает её недоступность, но не причину; не сообщать об успешно выполненном этим запросом удалении. Если запись по-прежнему видна, для нового удаления снова получить подтверждение с актуальной версией |

При подтверждённой потере прав или завершении сессии уничтожить защищённый
черновик и не переносить его в следующий вход. При продолжающемся сетевом
сбое результат остаётся неизвестным: доступно повторное чтение, не запись.
Гарантия от дубля создания ограничена сохранённым UUID текущего черновика.

Запросы Auth и REST из SPA ограничены 10 с на транспорт: при таймауте вход можно
повторить вручную; при таймауте изменения сначала применяется описанное выше
правило перечитывания. Смена аккаунта и отмена запроса сохраняют свой сигнал отмены.

## Окружения и поставка

| Окружение | Назначение и граница |
|---|---|
| Локальное | Supabase CLI как фиксированная dev-зависимость, Docker, миграции, отдельные тестовые данные и аккаунты |
| Локальные тесты | Изолированный project ID/порты; reset только этого проекта, фикстуры не используют облачные секреты |
| Облачное демо | Выделенный Supabase Cloud, те же миграции, signup выключен, демо-аккаунты создаются администратором |
| SPA hosting | Статический HTTPS-хостинг с fallback на SPA для прямых URL; поставщик и конкретный ресурс выбираются перед S8 |

Cloud не связан с локальным CLI на этапе Kit и документов. Создание ресурсов,
применение облачных миграций и публикация выполняются в отдельном разрешённом
этапе. До миграции демо фиксируются целевой проект, имеющиеся данные,
способ сохранения/восстановления и readback результата. Локальные тесты не
считаются свидетельством облачных настроек Auth или доступности приложения.

Будущая сборка и функциональные тесты SPA не зависят от приватного Kit.
На этапе сдачи проверяется clone GitHub без приватного submodule: установка,
сборка и документированные тесты приложения должны выполняться. Kit отдельно
нужен командам агента и проверки документации. Локальный результат этого пути фиксируется при проверке чистого clone.

### Активация чтения CRM

[Миграция 09](../supabase/migrations/20261104000009_rls_counts.sql) сохраняет данные и
существующую конфигурацию шлюза, создаёт проверку и закрывает клиентское чтение
четырёх таблиц. Штатные локальные команды применяют недостающие миграции и запускают
[активацию](../scripts/local-read-access.mjs). Она выполняет [настройку
PostgREST](../supabase/activation/configure-read-guard.sql) в конкретной БД и ждёт
HTTP 400 с кодом `PT400` и сообщением `UNSUPPORTED_READ_PREFERENCE` на GET
`/rest/v1/tasks?select=id&limit=0` с публичным ключом и `Prefer: count=planned`.
Второй запрос к тому же ресурсу без Prefer с `Accept: application/vnd.pgrst.plan+json`
должен получить 406/`PGRST107`: выдача планов должна быть выключена
(`db-plan-enabled=false`). Иначе [отдельный API EXPLAIN](https://docs.postgrest.org/en/stable/references/observability.html#execution-plan)
показывает статистику без заголовка подсчёта.
Сетевая ошибка, обычный 400, отказ в правах или неподтверждённый reload оставляют
чтение закрытым. Только ожидаемый ответ позволяет
[вернуть SELECT](../supabase/activation/restore-read.sql) роли authenticated; RLS продолжает действовать.

Перед выкладкой нужен выделенный проект. Проверить активный pre-request hook
и db-pre-config как в БД, так и в **эффективной конфигурации сервиса** (env/файл
PostgREST). При чужом hook, дополнительных API-ролях или схемах нельзя применять
локальную настройку вслепую: согласовать композицию проверок, область GET/HEAD и
права вызова для действующих ролей. При выключенном чтении конфигурации из БД
настроить шлюз через его владельца. На целевом URL проверить отказ до открытия
SELECT, затем разрешённые чтения и точные счётчики от обеих ролей. Изменение или
отключение hook после открытия таблиц не отзывает SELECT автоматически; при изменении
конфигурации шлюза проверку нужно повторить.

Для нового выделенного Supabase Cloud без восстановления и сторонней настройки
проверяются доступные настройки Management API, DB/role settings и функции БД.
Внутренние env/файл managed PostgREST оператору не доступны. Отсутствие стороннего
hook принимается как обоснованный вывод из происхождения проекта и документированных
defaults; это не утверждение об осмотре env. Перед открытием SELECT остаются обязательны
точные HTTP-проверки действующего guard и запрета планов. На новом проекте
`slgwsnfjxapsjpdzezui` обе проверки выполнены до открытия SELECT; затем пройдены
157 проверок реального Cloud API от анонимного клиента и трёх пользовательских сессий.
