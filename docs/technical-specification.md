# Техническая спецификация мини CRM

Статус: целевая архитектура принята к реализации, 2026-11-04.
SPA, SQL, миграции и тесты ещё не созданы. Продуктовый объём задают
[требования](business-requirements.md), а происхождение решений —
[журнал](decisions.md).

## Архитектура

Браузерная SPA обращается к Supabase Auth и Data API через официальный
Supabase SDK. PostgreSQL владеет данными, полномочиями, переходами и историей.
Отдельного backend-сервиса, workers или AI-функций для v1 не требуется.

Чтение бизнес-таблиц ограничивает RLS. Изменяющий API — семь узких database RPC;
прямые INSERT, UPDATE и DELETE для клиентских ролей отозваны. Клиент показывает
доступные действия, но окончательное решение всегда принимает база.

## Frontend

Один пакет с `src/app` для маршрутов и провайдеров, `src/modules/auth`,
`src/modules/objects`, `src/modules/tasks` для сценариев и `src/shared` для
реально повторяемых UI-примитивов и интеграционной инфраструктуры.
Модули публикуют явные точки входа; доменная логика не уходит в общий каталог.

| Область | Решение |
|---|---|
| Сборка и язык | Vite, React, TypeScript strict |
| Маршруты | TanStack Router |
| Серверное состояние | TanStack Query |
| Формы и ввод | React Hook Form, Zod |
| Интерфейс | Tailwind, app-local компоненты shadcn/Radix |
| Данные | Supabase SDK, типы из мигрированной схемы |
| Тесты | Vitest, React Testing Library, MSW, Playwright |

Точные совместимые версии и lockfile фиксируются на этапе S1; копирование
полного manifest Seller Platform не требуется. XState, React Compiler pilot,
монорепозиторий, NestJS и Go в согласованный стек не входят.

### Маршруты и состояние

| URL | Доступ и содержание |
|---|---|
| `/login` | Вход; активная сессия переводит на разрешённый экран |
| `/objects` | Список доступных объектов |
| `/objects/$objectId` | Объект и доступные задачи; действия постановщика |
| `/tasks/$taskId` | Данные, действия по роли и статусу, история |
| `/my-tasks` | Задачи текущего исполнителя |
| `/` | Постановщик → объекты; исполнитель → мои задачи; гость → вход |

Формы создания и редактирования размещаются в контексте списка или карточки;
отдельные публичные URL для них не обязательны. Меню и маршруты не открывают
управление аккаунтами. Переход по прямой ссылке проходит ту же авторизацию.

Сессию предоставляет SDK, активную роль — защищённый профиль БД. До определения
сессии и профиля защищённые данные не отображаются. Query keys включают ID
текущего пользователя; при выходе, смене пользователя или потере доступа
связанные запросы отменяются и кеш очищается. Данные кеша не являются
доказательством сохранённого доступа на сервере.

UI-состояние форм локально. Статус задачи не меняется оптимистически:
отображается подтверждённый ответ БД, затем инвалидируются карточка,
история и затронутые списки. Изменяющие запросы не имеют автоматических retry.

## Данные и API

Ниже — контракт для будущих миграций, а не уже существующая схема.
UUID используются для бизнес-записей и профилей, время хранится как
`timestamptz`, формируется БД и отображается в часовом поясе браузера с русской
локалью. Внешние пробелы обязательного ввода удаляются; пустое название,
адрес или обязательный комментарий не принимаются. Описание необязательно.
Пользовательский текст отображается как текст, без исполнения HTML.

### Сущности

| Сущность | Основные поля и ограничения |
|---|---|
| `profiles` | `id` → Auth user, `display_name`, `role` (`manager` или `executor`), `active`; клиент не создаёт и не меняет профиль, роль или активность |
| `objects` | `id`, `name`, `address`, `version`, `deleted_at`; обязательные имя и адрес |
| `tasks` | `id`, `title`, `description`, `object_id`, `assignee_id`, `status`, `author_id`, `created_at`, `version`, `deleted_at`; объект и назначенный активный исполнитель обязательны |
| `task_status_history` | Серверный последовательный `id`, `task_id`, `actor_id`, `occurred_at`, `from_status`, `to_status`, `comment`; клиент не задаёт поля события |

`version` — целое число, увеличиваемое базой при изменении или мягком удалении
записи. Автор и дата создания задачи неизменяемы. Для отображения имени автора
в задаче и имени участника в истории БД сохраняет их текстовые снимки при
создании записи; клиент не может подставить эти значения. Это позволяет читать
историю без открытия исполнителю чужих профилей или каталога аккаунтов.
Изменение имени аккаунта не переписывает исторические снимки.

Профили сохраняются при деактивации аккаунта; через приложение аккаунты не
удаляются. Внешние ключи истории не используют каскадное физическое удаление.
Индексы нужны по связям задачи с объектом и исполнителем, по истории задачи
и по условиям RLS; конкретный набор проверяется запросами реализации.

### Статусы

| Значение БД | Отображение |
|---|---|
| `new` | Новая |
| `in_progress` | В работе |
| `in_review` | На проверке |
| `accepted` | Принята |
| `rework` | На доработке |

Граф и роли переходов канонически заданы в
[требованиях](business-requirements.md#жизненный-цикл-задачи).
Создание задачи включает начальное событие `NULL → new` в той же транзакции.
Редактирование, перенос, переназначение и мягкое удаление не создают фиктивных
переходов. Отдельный аудит редактирования полей в объём v1 не входит.

### Чтение

SDK читает `objects`, `tasks`, `task_status_history` с RLS. История сортируется
по серверному последовательному ID от старых событий к новым. Профиль доступен
самому пользователю; постановщик также читает минимальный справочник профилей
для назначения активных исполнителей. Auth emails и административные поля
не включаются в публичный справочник. Исполнитель не получает чужие профили;
необходимые имена входят в снимки доступной ему задачи и её истории.

Списки, вложенные ответы и счётчики считают только видимые записи. Нельзя
возвращать исполнителю общий счётчик задач объекта или чужую историю через
вспомогательный запрос, view или RPC. Отдельный поиск чужих задач по ID
не создаётся.

### Изменяющие RPC

| Операция | Вход | Успех |
|---|---|---|
| `create_object` | Заранее созданный UUID, название, адрес | Каноническая новая запись объекта |
| `update_object` | ID, ожидаемая версия, название, адрес | Обновлённый объект и новая версия |
| `delete_object` | ID, ожидаемая версия | ID и версия мягко удалённого объекта; задачи скрыты атомарно |
| `create_task` | Заранее созданный UUID, название, описание, объект, исполнитель | Новая задача и начальное событие истории |
| `update_task` | ID, ожидаемая версия, название, описание, объект, исполнитель | Обновлённая задача с прежними статусом, автором и датой создания |
| `delete_task` | ID, ожидаемая версия | ID и версия мягко удалённой задачи |
| `transition_task` | ID, ожидаемая версия, целевой статус, необязательный комментарий | Обновлённая задача и одно новое событие истории |

Первые шесть операций разрешены только постановщику. В `transition_task`
роль, текущее назначение и переход проверяются по графу. Идентификатор
действующего пользователя всегда берётся из Auth, а не аргумента RPC.
Клиент не передаёт автора, дату, from-status, произвольный role или событие
истории. Поля каждого RPC явно перечислены; массового обновления произвольным
JSON-объектом нет. БД валидирует обязательный ввод независимо от Zod.

Перед первым запросом создания клиент генерирует UUID объекта или задачи и
сохраняет его в текущем черновике вместе с отправляемыми полями. Повтор того же
намерения использует тот же ID. Create выполняет только вставку: существующий
ID даёт отказ без перезаписи, повторного события истории или выдачи недоступной
записи; `upsert` для этого пути не используется. Одинаковые названия и поля
у разных записей допустимы и не служат способом корреляции.

### Атомарность и конкуренция

RPC блокирует затронутые строки, проверяет доступность и ожидаемую версию
после блокировки, затем выполняет весь эффект в одной транзакции. Несовпадение
версии даёт конфликт без частичного изменения. Конкурентные status-запросы
с одной версией дают один переход и одно событие.

Изменения задач согласуются с удалением родительского объекта. Порядок
блокировок: затронутые объекты в порядке ID, затем задачи в порядке ID;
доступность объекта проверяется под блокировкой. При переносе блокируются
исходный и целевой объекты. Поэтому создание или изменение задачи не может
зафиксироваться под уже удалённым объектом. Профиль назначения проверяется
как действующий исполнитель в этой же операции.

Удаление объекта помечает его и все ещё неудалённые задачи одной транзакцией,
увеличивая их версии. История остаётся неизменной. Удалённые записи исключаются
из RLS-чтения обеих бизнес-ролей; административный доступ вне API CRM
сохраняется для обслуживания. Клиент не получает RPC восстановления.

## Безопасность

### Источник полномочий

Авторизация использует активный профиль БД, привязанный к `auth.uid()`.
Пользовательские `user_metadata` и аргументы запроса не задают роль.
Профиль без роли, отсутствующий или неактивный профиль не получает бизнес-доступ.
Администратор может независимо от приложения запретить новые операции,
деактивировав профиль и заблокировав аккаунт в Supabase Auth; старый JWT не
восстанавливает бизнес-доступ. Смена роли не входит в клиентский API.

### Матрица чтения

| Данные | Постановщик | Исполнитель | Гость или неактивный профиль |
|---|---|---|---|
| Неудалённые объекты | Все | Только с текущими своими неудалёнными задачами | Нет |
| Неудалённые задачи | Все | Только с текущим `assignee_id = auth.uid()` и неудалённым объектом | Нет |
| История | Для доступной задачи | Для доступной собственной задачи | Нет |
| Профили | Свой и минимальный справочник | Только свой | Нет бизнес-доступа |
| Мягко удалённые записи | Нет через API CRM | Нет | Нет |

Политики задач и объектов не должны рекурсивно вызывать друг друга.
Если для роли или проверки видимости нужна вспомогательная функция,
она размещается в неэкспонируемой схеме `private`, проверяет текущий Auth ID
и не предоставляет произвольный обход RLS. Такие функции отдельно тестируются.

### Grants и функции

RLS включается на всех четырёх таблицах. У `anon` отзываются бизнес-права;
у `authenticated` остаётся только допустимое чтение. Прямые клиентские
INSERT, UPDATE и DELETE бизнес-таблиц и истории отзываются, включая возможность
изменить `role`, `deleted_at`, `version` или системные поля. Только служебные
пути создания пользователей и миграций используют привилегированную среду.

Изменяющие RPC используют `SECURITY DEFINER`, пустой `search_path` и полностью
квалифицированные имена. Они явно проверяют Auth, активный профиль, роль,
видимость ресурса, версию, ввод и переход; definer сам по себе не сохраняет
защиту RLS. `EXECUTE` отзывается у `PUBLIC` и `anon`; нужные функции выдаются
только `authenticated`. Права по умолчанию также закрываются для новых функций.
Вспомогательные функции не превращаются в доступный извне универсальный SQL API.

Историю вставляет только доверенный путь создания задачи или status-RPC.
Ни одна бизнес-роль не может создать произвольное событие, обновить или удалить
старое через прямой API или другой RPC. Ошибка вставки истории откатывает статус.

### Ключи и сессия

В браузере допустимы только публичный URL Supabase и publishable key
(либо эквивалентный публичный local anon key). `service_role`, secret key,
пароль БД и административные токены не входят в bundle, tracked-файлы,
логи или отчёты. Локальные env-файлы игнорируются, в примерах — только имена
переменных. При работе с session cache учитываются смена аккаунта и поздние
ответы отменённых запросов. Пользовательский текст отображается без HTML.

## Ошибки и согласованность

Адаптер Supabase преобразует ожидаемые отказы в категории: требуется вход,
нет полномочий на операцию, запись недоступна, конфликт версии, недопустимый
переход, ошибка ввода. Отсутствующая и чужая запись не различаются для
неавторизованного читателя. UI не показывает необработанный SQL, ключи или
детали внутренней ошибки. Конкретное кодирование отказов фиксируется вместе
с SQL и тестами S2, сохраняя эти категории.

При неизвестном результате mutation клиент перечитывает запись по известному
ID, версию и относящуюся историю. Для create ID уже известен из черновика,
даже если первый ответ потерян. Автоповтор не выполняется. Если запись
доступна, UI показывает сохранённый результат; отличающийся черновик не
перезаписывает его без отдельного редактирования.

Отсутствие доступной строки не доказывает отсутствие commit: запись могла
быть удалена или стать недоступной. Неопределённость показывается честно.
Явный повтор создания использует прежний UUID, а не новый: уникальность ID
не позволяет создать второй объект/задачу или второе начальное событие.
Для уже существующей записи повтор изменения использует перечитанную версию
и повторное подтверждение пользователя. Старая версия отклоняется.
Конфликт не уничтожает черновик. Уход со страницы при неизвестном результате
не запускает новый запрос и не сопровождается утверждением, что запись
не сохранена; безопасный повтор создания относится к одному сохранённому ID.

## Окружения и поставка

| Окружение | Назначение и граница |
|---|---|
| Локальное | Supabase CLI как фиксированная dev-зависимость, Docker, миграции, отдельные тестовые данные и аккаунты |
| Локальные тесты | Изолированный project ID/порты; reset только этого проекта, фикстуры не используют облачные секреты |
| Облачное демо | Выделенный Supabase Cloud, те же миграции, signup выключен, демо-аккаунты создаются администратором |
| SPA hosting | Статический HTTPS-хостинг с fallback на SPA для прямых URL; поставщик и конкретный ресурс выбираются перед S8 |

Cloud не связан с локальным CLI на этапе Kit и документов. Создание ресурсов,
применение облачных миграций и публикация выполняются в отдельном разрешённом
этапе. До миграции демо фиксируются целевой проект, имеющиеся данные,
способ сохранения/восстановления и readback результата. Локальные тесты не
считаются свидетельством облачных настроек Auth или доступности приложения.

Будущая сборка и функциональные тесты SPA не зависят от приватного Kit.
На этапе сдачи проверяется clone GitHub без приватного submodule: установка,
сборка и документированные тесты приложения должны выполняться. Kit отдельно
нужен командам агента и проверки документации. Этот путь пока не реализован.
