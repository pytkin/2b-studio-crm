# Облачная поставка демо

Этот документ описывает обслуживание Supabase Cloud Free и Vercel Hobby.
Для локального запуска используйте [руководство разработки](local-development.md).
Статус поставки ведётся в [плане](implementation-plan.md#s8-демо-и-сдача),
критерии — в [матрице приёмки](acceptance-plan.md), результаты Cloud/API,
свежего clone и браузерного цикла — в [отчёте S8](evidence/cloud-deployment/README.md).

## Предпосылки облачного обслуживания

Для операций ниже нужны установленные зависимости проекта и авторизованный
Supabase CLI с правами управления именно указанным Cloud-проектом. Выпуск SPA
требует прав на GitHub-репозиторий и проект Vercel. Эти административные доступы
передаются владельцу отдельно и не требуются для локального запуска CRM.
Секретные значения хранятся вне Git и не добавляются в браузерные `VITE_*`.

Аккаунты создаёт администратор с правами управления Supabase Auth через
Dashboard или Auth Admin API в доверенном окружении. Для каждого Auth user
необходимо явно назначить соответствующий профиль и роль; публичная SPA
не выдаёт эти полномочия. Локальный `demo:start` не создаёт Cloud-аккаунты.

## Граница доступа и конфигурация Vercel

Публичны оболочка SPA, исходники и публичный ключ Supabase. Данные CRM требуют
входа: роль и доступ к строкам проверяет PostgreSQL. Статический хостинг не
получает административный ключ или пароль БД. Для этого демо не нужны платный
план, SMTP или собственный домен.

Параметры проекта:

| Настройка | Значение |
|---|---|
| Framework | Vite |
| Root Directory | Корень репозитория |
| Node.js | `26.x`; приложение требует `>=26.12.1 <27` |
| Package manager | `pnpm@12.15.0` из `package.json` |
| Install Command | `pnpm install --frozen-lockfile` |
| Build Command | `pnpm build` |
| Output Directory | `dist` |

В Production и Preview заданы только три переменные:

- `VITE_SUPABASE_URL` — URL API из таблицы выше;
- `VITE_SUPABASE_PUBLISHABLE_KEY` — публичный publishable key этого проекта;
- `ENABLE_EXPERIMENTAL_COREPACK=1` — включение закреплённого package manager.

`VITE_*` попадают в браузерную сборку. `service_role`, secret key, пароль БД,
управляющие токены и пароли аккаунтов туда не добавляются. Изменение переменных
требует новой сборки. Сейчас Preview обращается к той же демо-базе, что и
Production: действия в Preview меняют общие демонстрационные данные.

[`vercel.json`](../vercel.json) задаёт возврат `index.html` для прямых SPA-маршрутов
и защитные HTTP-заголовки. Его CSP разрешает соединение с указанным Supabase API;
при смене проекта обновляются и переменные, и `connect-src`.
[`.vercelignore`](../.vercelignore) ограничивает состав сборки разрешёнными входами;
это подтверждено и журналом Git deployment.
Приватный Agent Platform Kit приложению не нужен; получатель устанавливает и
собирает приложение без инициализации submodule. Он нужен отдельно для агентских
и документальных проверок.

## Полученные свидетельства

[Отчёт S8](evidence/cloud-deployment/README.md) содержит readback deployment/commit,
журнал сборки, проверки публичных артефактов, 157 API-наблюдений и 39 браузерных
наблюдений на desktop/mobile со снимками. Там же указаны границы проверок и
непроверенный полный restore. JWT сессий, пароли и browser storage в отчёт
не входят. Этот runbook задаёт порядок следующих операций, а не заменяет
свидетельства уже выполненной приёмки.

Аккаунты находятся в игнорируемом локальном файле
`.local/cloud/demo-accounts.json` с правами `0600`. Значения не входят в Git,
логи, снимки или этот runbook. Доступы передаются получателю отдельно разрешённым
способом. Открытая регистрация остаётся выключенной; новые аккаунты создаёт
администратор с явным назначением профиля. Автоматическая отправка приглашений
и восстановление по почте в демо не настраивались.

## Последующие миграции и выпуск SPA

Подключённая GitHub-интеграция Vercel создаёт деплой при push; production
ветка обновляет публичную версию. Это поведение описано в
[документации Vercel](https://vercel.com/docs/git/vercel-for-github).
Изменение схемы БД выполняется отдельно управляемой операцией до публикации
зависимой версии SPA. Git push не применяет миграции Supabase.

Перед изменением базы владелец сверяет целевой ref, текущие миграции, реальные
данные, обратную совместимость старой SPA и способ восстановления. Сначала
проводятся локальные проверки миграции и регрессии доступа, затем создаётся
резервная копия по следующему разделу. Команды запускаются из корня checkout;
для агента используется префикс `rtk proxy`.

Для закреплённого Supabase CLI 3.0.0 цель задаётся явно через `--remote=<ref>`:

```sh
pnpm exec supabase migration list --remote=slgwsnfjxapsjpdzezui
pnpm exec supabase db push --remote=slgwsnfjxapsjpdzezui --skip-vault --dry-run
```

После проверки точного списка и разрешения операции:

```sh
pnpm exec supabase db push --remote=slgwsnfjxapsjpdzezui --skip-vault
pnpm exec supabase migration list --remote=slgwsnfjxapsjpdzezui
```

Пароли не передаются аргументами и не сохраняются в командах. CLI использует
авторизованное хранилище доступа; при интерактивном запросе пароль вводится
скрыто. `--skip-vault` сохраняет внешние Vault secrets и не переносит настройки
локального проекта. Не использовать облачный `reset`, локальные тестовые
фикстуры, `--include-seed` или массовое восстановление как способ обновить демо.

Для миграций, меняющих права чтения, guard или конфигурацию PostgREST, применяется
порядок [активации чтения CRM](technical-specification.md#активация-чтения-crm):

1. Сверить существующие pre-request hook, db-pre-config, API-роли, схемы и
   эффективную конфигурацию сервиса. Чужой hook требует согласованного объединения.
   До изменения guard закрыть SELECT четырёх CRM-таблиц; миграция 09 делает это
   при первой установке, последующая перенастройка шлюза требует отдельного отзыва.
2. Применить [настройку guard](../supabase/activation/configure-read-guard.sql)
   именно к целевой БД и дождаться reload PostgREST. Настройка не открывает таблицы.
3. На целевом HTTPS API с публичным ключом выполнить GET
   `/rest/v1/tasks?select=id&limit=0` с `Prefer: count=planned`. Требуется
   HTTP 400, код `PT400`, сообщение `UNSUPPORTED_READ_PREFERENCE`.
4. На том же URL без `Prefer`, с `Accept: application/vnd.pgrst.plan+json`,
   требуется HTTP 406 и код `PGRST107`. Обычный отказ в правах, иной ответ,
   timeout или неподтверждённый reload не засчитываются.
5. Только после двух ожидаемых ответов применить
   [`restore-read.sql`](../supabase/activation/restore-read.sql). Проверить
   разрешённые чтения и точные счётчики под обеими ролями, изоляцию чужих задач
   и запрет регистрации. При отказе проверки чтение остаётся закрытым.

После изменения или отключения hook SELECT не отзывается автоматически.
Повторная проверка на реальном шлюзе обязательна при такой перенастройке.
Перенос всех значений `supabase/config.toml` в облако не заменяет эту процедуру.

Перед push выполняется `pnpm verify`; при изменении БД или сквозного поведения —
соответствующие DB/API/E2E-проверки на выделенном локальном test-проекте.
Автоматическая сборка Vercel выполняет `pnpm build`; полного тестового CI gate
в этой поставке нет. Успех сборки не заменяет перечисленные проверки.

После успешного readback базы разрешается выпуск совместимой SPA. Для каждого
выпуска фиксируются commit, deployment ID/URL и результат короткой проверки входа
и ролей. Ошибка публикации сначала разбирается по build logs; секретные env и
сырой вывод с токенами не прикладываются к отчёту.

## Ограничения бесплатного демо

Supabase может приостановить Free-проект при низкой активности за семь дней;
возобновление выполняется в Dashboard. Перед показом нужно проверить вход и
доступность API. Это ограничение описано в
[правилах доступности Supabase](https://supabase.com/docs/guides/deployment/going-into-prod#availability).

Vercel Hobby разрешает личное некоммерческое использование. Здесь размещено
личное тестовое задание с демонстрационными данными; эксплуатация CRM для
клиентского бизнеса требует отдельного решения по подходящему тарифу и
условиям. См. [условия Hobby](https://vercel.com/docs/plans/hobby).

Supabase Advisor возвращает восемь предупреждений: семь относятся к намеренным
`SECURITY DEFINER` RPC, чьи полномочия проверены аудитом и запросами от реальных
ролей; восьмое — к выключенной защите от известных утёкших паролей. Последняя
доступна только на Pro и выше, как указано в
[документации Password security](https://supabase.com/docs/guides/auth/password-security).
В этом Free-демо используются случайные сильные пароли, аккаунты создаёт
администратор, открытая регистрация отключена. Предупреждение не объявляется
устранённым; платное обновление плана не выполнялось.

## Резервная копия и восстановление

На Free нельзя закладываться на доступную автоматическую резервную копию или
PITR. Supabase рекомендует регулярный ручной экспорт с хранением вне проекта;
см. [правила резервирования](https://supabase.com/docs/guides/platform/backups).
До внесения реальных данных и перед каждой меняющей их операцией нужен
проверенный ручной backup.

Владелец сохраняет роли, схему, данные и историю миграций по
[процедуре Supabase CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
В состав включаются бизнес-строки, Auth-пользователи и их связи с профилями;
настройки Auth и guard фиксируются отдельно без секретных значений. Один dump
схемы не является копией данных. Экспорт хранится с ограниченными правами вне
Git и каталога, загружаемого в Vercel; сохраняются время, ref, SHA, состав и
контрольные суммы. При появлении Storage его файлы требуют отдельной копии.

Восстановление сначала проверяется на отдельной явно разрешённой цели: схема,
профили/аккаунты, права, guard, вход и чтения обеих ролей. Проверка восстановления
ещё не проводилась; подготовку новой пустой базы нельзя считать её заменой.
Восстановление поверх текущей базы и удаление облачных ресурсов требуют
отдельного разрешённого объёма и учёта накопленных изменений.

Откат Vercel возвращает сборку SPA и не откатывает базу. Использовать предыдущую
сборку можно только при совместимой схеме. При несовместимости остановить
дальнейший выпуск и выбрать проверенную исправляющую миграцию либо согласованное
восстановление; `reset` облачной базы не является процедурой отката.
