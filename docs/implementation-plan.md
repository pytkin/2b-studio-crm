норму задают [требования](business-requirements.md), контракт —
[спецификация](technical-specification.md), критерии — [приёмка](acceptance-plan.md).

## S0 Kit и документы

Результат: Git-репозиторий, настоящий Kit submodule на принятом pin,
короткая точка входа, шесть деклараций операций, канонический review-change,
локальные маршруты и документы. Исходный DOCX сохранён побайтно с SHA-256.

Приёмка: `setup`, `lint`, `verify`, доступность ссылок и навыка, совпадение
gitlink/HEAD Kit, отсутствие зависимости от соседних checkout, соответствие
всем разделам задания и ответам пользователя. Выполняется одно независимое
read-only ревью в чистом контексте; подтверждённые P0–P2 устраняются.

Свидетельства фиксируются в [таблице подключения](agent-platform-onboarding.md).
Завершение — локальный commit с task-owned файлами. Публикация не входит в S0.

Приёмка 2026-11-04: setup/lint/verify прошли; 24 требования связаны с матрицей,
12 сценариев описаны. Независимое ревью в чистом контексте нашло один P2
в восстановлении после потерянного ответа create. Контракт UUID и API-04/FE-04
уточнены; повторное прицельное ревью закрыло P2 без новых замечаний.
Результат подтверждает только Kit и документацию, не поведение CRM.

## S1 Каркас

Создать один пакет SPA, согласованные провайдеры, пустые целевые маршруты,
UI-основу и интеграцию env без секретов. Выбрать совместимые версии, закрепить
Node/pnpm, manifest и lockfile. Добавить фиксированный Supabase CLI,
локальную конфигурацию с отдельным project ID и документацию запуска.

Заменить неприменимые операции реальными командами по мере появления кода.
Разделить проверки приложения и приватного Kit: чистая установка и сборка
SPA не требуют доступа к Kit. Установка приложения не запускает облачные действия.

Приёмка: INF-01 в части установки, typecheck, lint, сборки, локального
запуска и честной регистрации доступных тестов; INF-02 для env и bundle.

## S2 База и безопасность

Миграции четырёх таблиц, RLS/grants, private helpers, RPC, optimistic concurrency,
мягкое удаление и история. Create использует заранее известный UUID для
однозначного readback потерянного ответа без повторной вставки.
Локальные аккаунты/данные готовить изолированным
административным сценарием без tracked-паролей. Выключить local signup.
Стабильное кодирование отказов закрепить вместе с producer/consumer тестами.

Приёмка: DB-01–DB-09, API-01 в части Auth/signup, API-02–API-04 по серверной
границе. Нужны pgTAP и реальные пользовательские сессии; после них независимое
ревью безопасности до использования облачной среды.

## S3 Авторизация

Реализовать SC-01, роль, защищённые маршруты, сохранение действующей сессии,
истечение и очистку Query cache, включая поздние ответы старого пользователя.
Приёмка: относящиеся API-01, FE-02 и браузерный smoke входа обеих ролей.

## S4 Объекты

Реализовать SC-02–SC-04, формы, прямые URL и отображение доступных задач.
Приёмка: относящиеся DB-02/03/07, FE-01/04, E2E-02. Проверить пустой объект
постановщика и отсутствие чужих задач/счётчиков у исполнителя.

## S5 Задачи

Реализовать SC-05–SC-07, безопасные отображаемые имена, «Мои задачи»,
редактирование в любом статусе, перенос, переназначение и удаление.
Приёмка: DB-03/06/07/08, FE-01–FE-04, E2E-02; старый исполнитель теряет доступ.

## S6 Цикл статусов

Реализовать SC-08–SC-12, допустимые действия и комментарии, актуальную историю,
обработку конфликта/неизвестного результата. Приёмка: DB-04/05/08,
API-03/04, FE-03/04, E2E-01. Замоканные ответы не заменяют реальный полный цикл.

## S7 Сквозная приёмка

Закрыть все локальные строки R-01–R-20, реальные desktop/mobile и клавиатурные
сценарии, ошибки, timeout, retry, конфликт, сессию и негативный прямой API.
Проверить миграции на чистом локальном окружении. Получить независимое
ревью итогового результата и исправить подтверждённые P0–P2.

## S8 Демо и сдача

Перед внешними действиями определить проект Supabase, hosting, GitHub
owner/видимость и разрешённый объём публикации. Получить доступы через внешнее
хранилище, проверить существующие данные и способ восстановления, затем
применить миграции и создать демо-аккаунты без записи паролей в репозиторий.

Выполнить INF-03 и REL-01–REL-03 на фактических внешних границах, проверить
свежий GitHub clone без Kit. Написать объяснение руководителю на полстраницы
по реализованной системе и обновить список решений/ограничений. Отправку
внешнего сообщения согласовать как конкретное отдельное действие.

## Порядок обновления плана

После этапа записать статус, revision, требование → реализация → команда или
артефакт → наблюдаемый результат → предел свидетельства. Самопроверка каждого
изменения обязательна; независимое ревью — по риску и на приёмке. Новая
итерация проверок нужна после исправления или обнаружения незакрытой границы.
Не отмечать этап завершённым по одному наличию файла или объявленной команды.
