# Продуктовые требования мини CRM

Статус: принято к реализации, 2026-11-04. Приложение ещё не реализовано.

## Цель

Строительная компания ведёт объекты и связанные с ними задачи. Постановщик
назначает работу и проверяет результат. Исполнитель видит свою работу,
передаёт её на проверку и получает причину возврата. Система сохраняет
историю статусов и защищает данные даже при обращении в обход интерфейса.

Источник — [задание](source/assignment.md). Уточнения пользователя и
технические допущения перечислены в [журнале решений](decisions.md).
Ограничение задания в 2–3 часа отменено пользователем; функциональные
требования и требования безопасности выполняются полностью.

## Термины

| Термин | Значение |
|---|---|
| Объект | Стройка с названием и адресом |
| Постановщик | Пользователь, управляющий всеми объектами и задачами и проверяющий результат |
| Исполнитель | Пользователь, выполняющий назначенные ему задачи |
| Своя задача | Неудалённая задача, текущим исполнителем которой является пользователь |
| Рабочие данные | Неудалённые объекты и задачи; их доступность зависит от роли |
| Удаление | Исключение из рабочих данных с сохранением записи и истории в БД |
| История | Последовательность зафиксированных изменений статуса задачи |

Роли интерфейса называются «Постановщик» и «Исполнитель». Термин «руководитель»
в исходнике описывает постановщика, а не третью роль. Технический
администратор создаёт аккаунты через Supabase и не получает отдельный экран CRM.

## Пользователи и границы

Одна компания; несколько постановщиков и исполнителей. У аккаунта одна роль.
Постановщик управляет всеми рабочими данными, включая задачи другого
постановщика. Исполнитель не редактирует поля задачи или объекта и не назначает
исполнителя. Доступ к собственной задаче распространяется на всю её историю.

В обязательный объём не входят несколько компаний, совмещение ролей,
самостоятельная регистрация, интерфейс управления пользователями, сроки задач,
вложения, отдельный чат комментариев, уведомления и восстановление удалённых
записей через интерфейс.

## Требования

### Платформа и вход

| ID | Требование | Основание |
|---|---|---|

| R-02 | Вход по email и паролю, выход, закрытая регистрация и ручное создание аккаунтов | ТЗ §2.5, §3; выход — допущение v1 |
| R-03 | Две роли, несколько пользователей каждой роли; у аккаунта одна роль | ТЗ §2.1 и уточнение пользователя |

### Объекты и задачи

| ID | Требование | Основание |
|---|---|---|
| R-04 | Постановщик создаёт, изменяет и удаляет объекты; поля объекта — название и адрес | ТЗ §2.1–2.2 |
| R-05 | Список объектов и карточка объекта с задачами и статусами; исполнитель видит только объекты со своими задачами и только свои задачи внутри них | ТЗ §2.1–2.2, §2.5 |
| R-06 | Постановщик создаёт, изменяет и удаляет задачи, выбирает объект и исполнителя; задача содержит название, описание, объект, исполнителя, статус, автора и дату создания | ТЗ §2.1, §2.3 |
| R-07 | Задача создаётся в статусе «Новая»; автор и дата создания определяются сервером и не редактируются | ТЗ §2.3 и допущение v1 |
| R-08 | Назначенный исполнитель начинает новую задачу, отправляет работу на проверку и возобновляет доработку | ТЗ §2.3 |
| R-09 | Постановщик принимает результат либо возвращает на доработку с обязательным комментарием | ТЗ §2.3 |
| R-10 | Разрешены только перечисленные ниже переходы; проверка выполняется базой | ТЗ §2.3, §3 |
| R-11 | Каждый переход сохраняет автора действия, время, предыдущий и новый статус и комментарий, если он есть; история доступна обеим ролям в пределах доступа к задаче | ТЗ §2.4 |
| R-12 | Карточка показывает данные, историю и только доступные текущему пользователю действия | ТЗ §2.5 |
| R-13 | Экран «Мои задачи» показывает исполнителю все его неудалённые задачи, включая принятые | ТЗ §2.5 и допущение v1 |
| R-17 | Постановщик редактирует рабочие поля и исполнителя в любом статусе, сохраняя статус, автора, дату и историю; прежний исполнитель теряет доступ после переназначения | Уточнение пользователя |
| R-18 | Удаление мягкое; удаление объекта скрывает также все его задачи, сохраняя историю; восстановления в интерфейсе нет | Уточнение пользователя |

| ID | Требование | Основание |
|---|---|---|

## Жизненный цикл задачи

| Из статуса | В статус | Кто | Комментарий |
|---|---|---|---|
| — | Новая | Постановщик при создании | Необязателен |
| Новая | В работе | Назначенный исполнитель | Необязателен |
| В работе | На проверке | Назначенный исполнитель | Необязателен |
| На проверке | Принята | Постановщик | Необязателен |
| На проверке | На доработке | Постановщик | Обязателен, не из одних пробелов |
| На доработке | В работе | Назначенный исполнитель | Необязателен |

Смена статуса выполняется отдельным действием, а не редактированием поля.
Из «Принята» переходов нет. Удаление и переназначение не являются переходами
статуса. Технические значения и атомарность описаны в
[спецификации](technical-specification.md#данные-и-api).

## Критерий завершения приложения

Все R-01–R-24 выполнены и связаны с проверяемыми свидетельствами в
[матрице приёмки](acceptance-plan.md). Успешный интерфейс не заменяет
отрицательные запросы к Supabase от разных ролей. Работающее локальное
приложение не заменяет проверку доступности публичного демо.

Критерий завершения текущего этапа Kit и документов находится отдельно в
[плане разработки](implementation-plan.md#s0-kit-и-документы).
