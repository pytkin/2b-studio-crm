# Локальная разработка и проверки

Команды выполняются из корня checkout. Установка Node, pnpm, Docker, Bash и Git описана в [README](../README.md#запуск-демо). Инструкции ниже используют Bash и локальный Docker с Unix-сокетом. Локальная приёмка выполнена на macOS с Docker Desktop; нативный Windows не поддерживается, WSL2 отдельно не проверялся.

## Демо

```sh
pnpm demo:start
```

Команда устанавливает зависимости по lockfile, запускает Supabase, применяет новые миграции, подготавливает три аккаунта, объекты и задачи, затем запускает production-сборку на **http://127.0.0.1:5173**. Supabase CLI 3.0.0 устанавливается как зависимость проекта; отдельно устанавливать CLI не нужно.

Логины и пароли находятся в `.local/demo-accounts.json` с правами `0600`. Для полного цикла откройте постановщика и исполнителя в разных профилях браузера. Доступы и данные сохраняются между запусками. Файл доступов не включается в Git и отчёты.

Остановка из того же checkout, где запускалось демо:

```sh
pnpm demo:stop
```

Останавливаются веб-сервер и Supabase; том базы сохраняется. Если запуск прервался, команда сообщает, удалось ли остановить созданный стек.

## Разработка с горячей перезагрузкой

Для первого запуска подготовьте миграции и аккаунты командой демо. После её остановки **снова запустите Supabase**, поскольку `demo:stop` останавливает и базу:

```sh
pnpm demo:start
pnpm demo:stop
pnpm db:dev start
```

Vite читает URL и публичный ключ локального API из `.env.local`. Следующий блок предназначен для **отсутствующего файла**: он создаёт его с правами `0600`, отбирает только две публичные переменные и отказывается перезаписывать существующий файл. Выполняйте в Bash:

```bash
(
  set -euo pipefail
  umask 077
  set -o noclobber
  if [ -e .env.local ] || [ -L .env.local ]; then
    printf '%s\n' '.env.local уже существует; сохраните его и проверьте настройки вручную.' >&2
    exit 1
  fi
  pnpm exec supabase status -o env 2>/dev/null |
    sed -n \
      -e 's/^API_URL=/VITE_SUPABASE_URL=/p' \
      -e 's/^PUBLISHABLE_KEY=/VITE_SUPABASE_PUBLISHABLE_KEY=/p' \
      > .env.local
  test "$(sed -n '$=' .env.local)" = 2
)
```

Не запускайте Vite, если блок завершился с ошибкой. Существующий `.env.local` сохраните и проверьте его настройки вручную по [.env.example](../.env.example): для этой среды URL — `http://127.0.0.1:56321`, ключ — публичный ключ этого локального проекта. В браузерную конфигурацию не добавляют `service_role`, secret key, пароль БД или управляющий токен. Полный вывод `supabase status` содержит административные значения: не прикладывайте его к переписке и отчётам.

```sh
pnpm dev
```

Откройте адрес, показанный Vite. После работы остановите Vite через `Ctrl+C`, затем выполните:

```sh
pnpm db:dev stop
```

При следующих запусках достаточно `pnpm db:dev start` и `pnpm dev`, если зависимости установлены, `.env.local` настроен и аккаунты уже подготовлены. После изменения зависимостей выполните `pnpm install --frozen-lockfile`; при необходимости обновления демо-данных используйте повторный `demo:start`, который сохраняет существующие записи.

## Сборка и проверки без базы

```sh
pnpm install --frozen-lockfile
pnpm verify
```

`verify` запускает lint, строгую типизацию, тесты команд и компонентов, production-сборку и сканирование артефактов на привилегированные ключи, JWT сессий и известные демо-пароли. Для этих проверок не нужны работающий Docker, приватный Kit или облачные аккаунты. `pnpm build` отдельно выполняет типизацию и сборку в `dist`.

Дополнительно `pnpm test:mutation` проверяет выбранные мутации распознавания публичного ключа и HTTP-защиты чтения. Он также не использует Docker или учётные данные; [назначение и пределы проверки](evidence/negative-mutation.md).

## Проверки с базой и браузером

Используется отдельный локальный проект **test**. Следующий reset полностью пересоздаёт только его базу; не сохраняйте в ней рабочие данные. DB/API/E2E запускаются последовательно, без параллельного использования этой тестовой базы другим checkout:

```sh
pnpm install --frozen-lockfile
pnpm db:test start
pnpm db:test reset
pnpm test:db
pnpm test:api
pnpm exec playwright install chromium
pnpm test:e2e
pnpm db:test stop
```

`test:db` выполняет pgTAP, `test:api` — запросы настоящих пользовательских сессий, в том числе конкуренцию и потерянный ответ. `test:e2e` запускает Chromium на desktop и mobile с реальными Auth и PostgreSQL. Браузер достаточно установить один раз и повторять установку после обновления Playwright. На Linux при отсутствии системных библиотек воспользуйтесь [инструкцией Playwright](https://playwright.dev/docs/browsers#install-system-dependencies).

Если проверка завершилась с ошибкой, выясните причину и отдельно выполните `pnpm db:test stop`. Для передачи результатов берите только безопасный каталог `test-results/run-…`, указанный в конце браузерного прогона. Сырой временный контекст браузера может содержать доступы.

## Среды, порты и безопасность локального стека

| Среда | Конфигурация | Project ID | API / PostgreSQL | Shadow DB | Блокировка |
|---|---|---|---|---|---|
| Разработка и демо | [supabase/config.toml](../supabase/config.toml) | `2b-studio-crm-dev` | 56321 / 56322 | 56320 | 56319 |
| Автотесты | [local/test/supabase/config.toml](../local/test/supabase/config.toml) | `2b-studio-crm-test` | 56421 / 56422 | 56420 | 56419 |

Обе среды используют PostgreSQL 17, Auth, PostgREST и одну [директорию миграций](../supabase/migrations). Регистрация отключена; локальные аккаунты создаёт команда подготовки. Среды имеют разные контейнеры, порты и тома. Checkout и worktree одного проекта на машине используют одни Docker-ресурсы; кратковременная блокировка на `127.0.0.1` защищает изменение состояния стека.

API, PostgreSQL и веб-сервер публикуются на loopback. Команды закрепляют локальный Docker-сокет, отклоняют удалённый host/context и проверяют реальные привязки контейнеров. Если сохранился старый контейнер с открытыми портами, остановите соответствующую среду через `pnpm db:dev stop` или `pnpm db:test stop`, затем запустите её снова. Остановка сохраняет данные. Dev reset запрещён.

После девятой миграции чтение CRM-таблиц закрыто до проверки шлюза. `demo:start`, `db:dev start`, `db:test start` и `db:test reset` автоматически проверяют два ожидаемых HTTP-отказа, затем возвращают чтение через RLS. Ручной SQL import эту настройку не завершает. Для облачного проекта действует отдельный [порядок активации](technical-specification.md#активация-чтения-crm).

При ошибке старта проверьте, что Docker запущен, выбран локальный context, Engine имеет версию 28+ и порты из таблицы свободны. `pnpm db:dev status` и `pnpm db:test status` показывают состояние без ключей. Не запускайте прямые облачные команды или сброс рабочей базы для исправления локального окружения.
