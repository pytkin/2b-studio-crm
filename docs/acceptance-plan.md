## База и прямой API

Использовать мигрированный локальный Supabase. Фикстуры: два постановщика,
два исполнителя, аккаунт без активного профиля, гость; несколько объектов,
включая пустой, задачи разных пользователей во всех пяти статусах и история.
Привилегии допустимы для подготовки и проверки сохранённых фикстур, но
защищаемые действия выполняются с реальной ролью/сессией проверяемого пользователя.

| ID | Сценарии проверки |
|---|---|
| DB-01 | RLS на всех бизнес-таблицах; grants таблиц и функций; прямые DML закрыты; definer-функции имеют безопасный search_path и ограниченный EXECUTE |
| DB-02 | Оба постановщика видят все рабочие данные; исполнители — свои задачи, их историю и только соответствующие объекты; гость и неактивный профиль не читают бизнес-данные |
| DB-03 | Создание/изменение обязательных полей, проверка активного исполнителя и объекта; server-owned поля; начальное событие и задача фиксируются вместе; создание с другим статусом запрещено |
| DB-04 | Все пары пяти статусов для постановщика, назначенного и чужого исполнителя, гостя и неактивного профиля; только разрешённые переходы успешны; пустой/пробельный комментарий возврата запрещён |
| DB-05 | Подделка события через INSERT, изменение и DELETE истории запрещены; попытка сменить actor/time/from-status через API не проходит; ошибка записи истории откатывает статус |
| DB-06 | Изменение рабочих полей, переназначение и перенос в каждом статусе не меняют status/author/created_at/старые события; прежний исполнитель теряет задачу и историю, новый получает её; доступ к объектам пересчитывается |
| DB-07 | Мягкое удаление задач во всех статусах; удаление объекта со смешанными задачами; записи и история сохранены административно, но не читаются бизнес-ролями; клиентское восстановление невозможно |
| DB-08 | Два запроса с одной версией, параллельное редактирование и переход, удаление объекта одновременно с созданием/переносом/переходом задачи; нет потерянной записи, частичного результата или двойной истории |
| DB-09 | Пользователь не меняет role/active, не создаёт себе профиль; user_metadata не даёт полномочий; деактивация профиля блокирует операции с ещё действующим JWT |
| API-01 | Вход, неверный пароль, выход, восстановление действующей сессии, истечение и отказ обновления сессии; прямой signup отключён локально и отдельно в демо |
| API-02 | Прямые REST-запросы, nested select и count повторяют RLS; неизвестный и чужой ID не раскрывают данные; после переназначения/удаления старые сессии не читают ресурс |
| API-03 | Прямые DML и RPC с неверной ролью, чужими ID, лишними системными полями и некорректным вводом; общие разрешения не обходятся вспомогательным RPC |
| API-04 | Одновременные RPC и потеря ответа после commit; create объекта и задачи используют заранее известный UUID, readback по нему однозначен даже при одинаковых полях разных записей; повтор того же UUID не создаёт дубликат/второе начальное событие и не перезаписывает данные; недоступная строка не выдаётся за доказанный rollback; повтор update со старой версией отклоняется |

DB-проверки выполняются pgTAP; многосессионная конкуренция и сетевые условия —
интеграционными TypeScript-тестами через SDK/REST. SQL-тест от `postgres`
без переключения роли не подтверждает пользовательскую авторизацию.

## Frontend и браузер

| ID | Проверка |
|---|---|
| FE-01 | Обязательные поля, пробельный комментарий, локальные ошибки, сохранение ввода, отмена формы и фокус |
| FE-02 | Кеш разделён по пользователям; logout/login, истечение сессии и поздний ответ старого запроса не показывают предыдущие данные |
| FE-03 | Матрица кнопок по роли, назначению и статусу; канонические русские подписи; pending не допускает двойного нажатия |
| FE-04 | Загрузка, пустой результат, error/timeout, безопасные сообщения, readback неизвестного mutation; UUID create-черновика сохраняется при ручном retry, новый ID автоматически не создаётся; конфликт сохраняет черновик, недоступный readback явно остаётся неопределённым |
| E2E-01 | Вход постановщика, создание задачи; исполнитель начинает и отправляет; постановщик возвращает с причиной; исполнитель повторяет цикл; постановщик принимает; обе роли читают историю |
| E2E-02 | Объекты/задачи CRUD, «Мои задачи», прямые ссылки, редактирование принятой задачи, переназначение и удаление; второй исполнитель не видит чужое |
| E2E-03 | Основные маршруты, формы и цикл задачи на 1440×900 и 360×800; клавиатура, доступные имена, фокус, читаемые статусы без зависимости только от цвета |
| E2E-04 | Реальный UI при сетевом отказе, timeout, конфликте и истёкшей сессии; успех не заявляется до подтверждения и введённый текст не теряется |

Vitest/RTL/MSW проверяют локальное поведение; Playwright — пользовательский
путь с реальными локальными Auth и БД. Mocked backend не закрывает DB/API-строки.
Для визуального вывода сохраняются проверенные скриншоты с фактическими размерами.

## Окружения

| ID | Проверка |
|---|---|
| INF-01 | Чистая установка по lockfile, typecheck, lint, тесты, production build; локальная схема воспроизводится миграциями и контролируемым seed |
| INF-02 | Tracked-файлы, env-примеры, bundle, test artifacts и логи не содержат привилегированных ключей, токенов или облачных паролей; диагностика не печатает найденные значения |
| INF-03 | Cloud project ref и применённые миграции совпадают с выбранным демо; signup закрыт, RLS/RPC проверены реальными ролями; reset локального окружения не затрагивает демо |

## Сдача

| ID | Что требуется |
|---|---|
| REL-01 | HTTPS URL, прямые SPA-маршруты, вход обеих ролей; минимум один постановщик и два исполнителя, 2–3 объекта и разные статусы; проверка публичной границы после публикации |
| REL-02 | GitHub ref/commit readback; свежий clone без приватного Kit позволяет по README установить, проверить и собрать приложение; миграции присутствуют, секреты отсутствуют |
| REL-03 | Объяснение для руководителя на полстраницы и актуальный журнал решений/ограничений; описание не обещает непроверенные свойства |

Доступы демо передаются отдельно от репозитория и отчётов. Условия hh.ru и
созвона сохранены как контекст исходника; отправка сообщения или назначение
созвона в этот этап не входят. Перед внешней сдачей нужна независимая проверка
соответствия результата требованиям. Разрешение и цель публикации фиксируются
отдельно от успеха локальных проверок.
