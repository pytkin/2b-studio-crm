## Когда принимается проверка

- **S3–S6:** каждую форму или экран принимают отдельно на фикстуре S2. Проверки FE называют событие, число запросов и состояние экрана; права и сохранённые данные проверяют под реальной сессией. Наличие следующего экрана не требуется.
- **E2E-02a — S4:** S4-01 владеет видимостью списка и карточки, S4-02 — созданием и правкой объекта, S4-03 — отменой и подтверждением каскада. Перед тестом подготовить объекты и задачи в БД. Исполнителю достаточно посмотреть список и строки задач в объекте.
- **E2E-02b — S5:** S5-01 владеет «Моими задачами» и карточкой, S5-02 — созданием, правкой принятой задачи и переназначением, S5-03 — отзывом доступа и удалением задачи. Принятая задача — фикстура; кнопки переходов S6 не нужны.
- **S7:** S7-01 впервые соединяет роли и экраны в E2E-01, повторяет обе части E2E-02 и собирает E2E-03/04. S7-02 сверяет локальные результаты. Для R-20 локальная часть INF-01 и демо INF-03 получают отдельные результаты. Полное требование остаётся открытым до обеих проверок.

## База и прямой API

Использовать мигрированный локальный Supabase. Фикстуры: два постановщика,
два исполнителя, отдельные аккаунты без профиля и с неактивным профилем, гость; несколько объектов,
включая пустой, задачи разных пользователей во всех пяти статусах и история.
Привилегии допустимы для подготовки и проверки сохранённых фикстур, но
защищаемые действия выполняются с реальной ролью/сессией проверяемого пользователя.

| ID | Сценарии проверки |
|---|---|
| DB-01 | RLS на всех бизнес-таблицах; grants таблиц и функций; прямые DML закрыты; definer-функции имеют безопасный search_path и ограниченный EXECUTE |
| DB-02 | Оба постановщика видят все рабочие данные; исполнители — свои задачи, их историю и только соответствующие объекты; гость и неактивный профиль не читают бизнес-данные |
| DB-03 | Создание/изменение обязательных полей, проверка активного исполнителя и объекта; server-owned поля; начальное событие и задача фиксируются вместе; с комментарием создания история содержит его текст, без комментария — null; создание с другим статусом запрещено |
| DB-04 | Все пары пяти статусов для постановщика, назначенного и чужого исполнителя, гостя и неактивного профиля; только разрешённые переходы успешны; пустой/пробельный комментарий возврата запрещён |
| DB-05 | Подделка события через INSERT, изменение и DELETE истории запрещены; попытка сменить actor/time/from-status через API не проходит; ошибка записи истории откатывает статус |
| DB-06 | Изменение рабочих полей, переназначение и перенос в каждом статусе не меняют status/author/created_at/старые события; прежний исполнитель теряет задачу и историю, новый получает её; доступ к объектам пересчитывается |
| DB-07 | Мягкое удаление задач во всех статусах; удаление объекта со смешанными задачами; записи и история сохранены административно, но не читаются бизнес-ролями; клиентское восстановление невозможно |
| DB-08 | Два запроса с одной версией, параллельное редактирование и переход, удаление объекта одновременно с созданием/переносом/переходом задачи; сверить ответы, конечные поля, версии и число событий для обоих порядков по [допустимым исходам](technical-specification.md#атомарность-и-конкуренция) |
| DB-09 | Пользователь не меняет role/active, не создаёт себе профиль; user_metadata не даёт полномочий; деактивация профиля блокирует операции с ещё действующим JWT |
| API-01 | Вход, неверный пароль, выход, восстановление действующей сессии, истечение и отказ обновления сессии; прямой signup отключён локально и отдельно в демо |
| API-02 | Прямые REST-запросы, nested select и count повторяют RLS; неизвестный и чужой ID не раскрывают данные; после переназначения/удаления старые сессии не читают ресурс |
| API-03 | Прямые DML и RPC с неверной ролью, чужими ID, лишними системными полями и некорректным вводом; общие разрешения не обходятся вспомогательным RPC |
| API-04 | После отправки отбросить ответ и выполнить readback как тот же пользователь. Для обоих create — исходный UUID, запись среди одноимённых, явный повтор без дубля. Для update/переназначения — фактические поля и версия; для transition — статус, автор и число событий; для delete — только видимость. Повтор со старой версией видимой записи даёт CONFLICT, чужой задачи для transition — UNAVAILABLE. Сверить состояние БД и отдельно сообщение/допустимое действие UI (FE-04) по [контракту восстановления](technical-specification.md#если-ответ-не-дошёл). |

DB-проверки выполняются pgTAP. В DB-08 два клиента SDK/REST вызывают RPC
с независимыми пользовательскими сессиями. Только в изолированной локальной
БД тестовый координатор удерживает общую для этих команд строку объекта
(`SELECT ... FOR UPDATE`). Запустить первый вызов и дождаться видимой блокировки
в `pg_blocking_pids`; затем запустить второй и дождаться его блокировки в той
же цепочке. Освободить строку, получить оба ответа и сверить результат с БД.
На свежей фикстуре поменять порядок вызовов. В отчёте отметить ожидающие
соединения и порядок; timeout ожидания — сбой теста, а не доказательство гонки.
Координатор не выполняет бизнес-операции от имени клиента. Для API-04 сетевой
посредник отбрасывает **ответ** уже выполненного запроса; отдельный контроль
блокирует сам **запрос** до сервера. Клиент не знает, какой случай произошёл.
SQL-тест от `postgres` без переключения роли не подтверждает пользовательскую авторизацию.

## Frontend и браузер

| ID | Проверка |
|---|---|
| FE-01 | Обязательные поля, пробельный комментарий, локальные ошибки, сохранение ввода, отмена формы и фокус |
| FE-02 | Раздельные кеши сессий; выход, истечение и подтверждённая потеря доступа очищают соответствующие данные и черновики. Имитировать возврат во вкладку, навигацию, восстановление сети и действие по отдельности; ответ старого запроса не восстанавливает закрытую карточку. |
| FE-03 | Матрица кнопок по роли, назначению и статусу; канонические русские подписи; pending не допускает двойного нажатия |
| FE-04 | Загрузка, пустой результат, error/timeout, безопасные сообщения, readback неизвестного mutation; UUID create-черновика сохраняется при ручном retry, новый ID автоматически не создаётся; конфликт при сохранённом доступе оставляет черновик только тому же пользователю; при недоступном readback исход запроса остаётся неизвестным |
| E2E-01 | Вход постановщика, создание задачи; исполнитель начинает и отправляет; постановщик возвращает с причиной; исполнитель повторяет цикл; постановщик принимает; обе роли читают историю |
| E2E-02a | На фикстуре со смешанными задачами постановщик создаёт и изменяет объект, исполнитель видит только свои строки; после подтверждённого удаления объект и его задачи исчезают при новом чтении обеих ролей. |
| E2E-02b | На фикстурах пяти статусов проверить создание/правку задачи, «Мои задачи», прямые ссылки, перенос и переназначение принятой задачи, удаление. Старый исполнитель теряет доступ, новый получает задачу с прежней историей. |
| E2E-03 | Основные маршруты, формы и цикл задачи на 1440×900 и 360×800; клавиатура, доступные имена, фокус, читаемые статусы без зависимости только от цвета |
| E2E-04 | Реальный UI при сетевом отказе, timeout, конфликте и истёкшей сессии; успех не заявляется до подтверждения; при конфликте с действующим доступом ввод сохраняется. После потери прав или истечения сессии защищённый ввод очищен, следующий аккаунт его не видит |

Vitest/RTL/MSW проверяют локальное поведение; Playwright — пользовательский
путь с реальными локальными Auth и БД. Mocked backend не закрывает DB/API-строки.
Для визуального вывода сохраняются проверенные скриншоты с фактическими размерами.

Доступы демо передаются отдельно от репозитория и отчётов. Условия hh.ru и
созвона сохранены как контекст исходника; отправка сообщения или назначение
созвона в этот этап не входят. Перед внешней сдачей нужна независимая проверка
соответствия результата требованиям. Разрешение и цель публикации фиксируются
отдельно от успеха локальных проверок.
